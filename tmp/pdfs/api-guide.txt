Server URL
Production (use this one):
https://game.daketi.pk
Nginx terminates TLS here and proxies to the Node server, WebSocket upgrade included. No
port number - it's plain 443.

Socket.io Setup
Flutter Dependencies
Add to pubspec.yaml :
dependencies:
  socket_io_client: ^2.0.0
  http: ^0.13.0
  flutter_riverpod: ^2.3.0
Initialize Socket Connection
transports: ['websocket']  is required, not optional. The server only accepts WebSocket
connections (no HTTP long-polling) - this is what lets the backend run multiple worker
processes (pm2 cluster mode) without needing sticky sessions. If you omit this option, the
client's default polling-ﬁrst handshake will simply fail to connect.

{
  "success": true,
  "stats": {
    "activeGames": 5,
    "connectedPlayers": 20,
    "activeRooms": 8
  }
}
Note: 
activeGames  counts every game record still in storage (Redis keys with an unexpired
TTL - 1 hour after last save), not how many games currently have someone actively playing.
A ﬁnished or abandoned game still counts here until its TTL runs out. connectedPlayers  is the
more "live" number - it's deleted immediately on disconnect, so it accurately reﬂects who's
connected right now.
3. Create Solo Game (you + AI opponents)
POST /api/game/solo
Content-Type: application/json
{
  "playerName": "John",
  "aiCount": 1,
  "difficulty": "master"
}
aiCount  is optional, clamped to 1-3 (default 1). T otal seats in the room = aiCount + 1  (you).
difficulty  is optional: "beginner"  or "master"  (default "master" ). Applies to every AI
opponent in the room. Beginner AI avoids stealing from opponents and picks moves without
optimizing card value; Master AI plays the existing optimal strategy (prioritizes high-value
steals and captures).
Response:
{
  "success": true,
  "gameId": "4821",
  "playerName": "John",
  "gameState": { /* game state object, status: "wai ting" */ }
}
Note: this response does not include a 
playerId . The AI players already have internal IDs,
but your playerId  is only assigned once you actually join over the socket (see Join Game
below) - the REST call just reserves the room.

6. Leaderboard
GET /api/leaderboard?limit=20
Public - no auth needed. Ranked by games won, ties broken by total score.
Response:
{
  "success": true,
  "leaderboard": [
    { "user_id": "e13bcab0-...", "name": "John", "g ames_played": 12, "games_won": 5, 
"total_score": 430 }
  ]
}
limit  defaults to 20 and is clamped to 1-100 (an out-of-range or non-numeric value is
clamped, not rejected). Keys are snake_case , like the other stats payloads.
Only players who ﬁnished a game while logged in appear here - see User Accounts for
what "logged in" means at the socket layer. A brand-new deployment's leaderboard is
legitimately empty; that's not a bug.
The admin-only 
/api/dashboard/*  endpoints also exist, but they back the web admin
dashboard and require an admin  role - nothing in the app should call them.
Game IDs
gameId  is a 4-digit numeric string (e.g. "0472" ), not a UUID - short enough to read aloud
or type when sharing a room with friends. It's zero-padded, so treat it as a string everywhere,
not a number (
"0472"  !== 472 ). It's randomly generated per game and only unique among
currently-active games (games expire from storage after being idle, so codes do get reused
over time).
User Accounts (Signup / Login)
A user account is a persistent Postgres-backed identity, distinct from the freely-typed
playerName  you pass to join_game . Playing still doesn't require an account - guests can play
every game mode exactly as before.
What being logged in buys you: pass the account's JWT as 
token  on join_game  (see Join
Game) and every ﬁnished game gets recorded against the account - which is what powers
/api/auth/me  stats, /api/auth/me/history  and the public leaderboard. Without that token ,
the player is a guest and nothing is saved.

Every response is JSON with a success  boolean; failures carry { "success": false, "error": "
<human-readable message>" } . The error  strings are written to be shown to the user as-is.
The user object
Every endpoint that returns a user returns this exact shape:
{
  "id": "e13bcab0-8ffb-440e-875b-f79063d8f626",
  "name": "John",
  "email": "john@example.com",
  "emailVerified": false,
  "role": "user",
  "dateOfBirth": "1990-05-15",
  "createdAt": "2026-08-11T08:20:05.378Z",
  "facebookLinked": false,
  "hasPassword": true
}
role  is "user"  or "admin" . Admin only gates the web admin dashboard
( /api/dashboard/* ) - the app has no admin surface, so you can ignore it.
dateOfBirth  is null  until the user sets it, and always plain YYYY-MM-DD  (never a full
timestamp) - safe to feed straight into a date picker.
facebookLinked  / hasPassword  say which ways this account can sign in - see Facebook
Login / Signup. A Facebook-only account has hasPassword: false  and may have email:
null .

1. Signup
POST /api/auth/signup
Content-Type: application/json
{
  "name": "John",
  "email": "john@example.com",
  "password": "at-least-8-characters"
}
Response (201): 
{ "success": true, "token": "eyJhbGciOi...", "user" : { ... } }
A veriﬁcation email is sent automatically, ﬁre-and-forget: signup still succeeds (and still
returns a usable token) if SES is having a bad moment. The new user is logged in
immediately with 
emailVerified: false  - nothing is gated on veriﬁcation today, so don't
block the app on it.
Errors: 
400  for a missing name, invalid email format, or a password under 8 characters; 409
( "Email is already registered" ); 429  if rate-limited.
Note: signup does not accept dateOfBirth . Collect it after signup with PATCH /api/auth/me  if
you want it during onboarding.
Signup also accepts an optional 
referralCode  - see Signing Up With a Code.
2. Login
POST /api/auth/login
Content-Type: application/json
{
  "email": "john@example.com",
  "password": "at-least-8-characters"
}
Response (200): same shape as signup (
{ success, token, user } ).
Error: 401  with "Invalid email or password"  for either a wrong password or an unregistered
email - deliberately the same message for both, so a client can't use this endpoint to
enumerate which emails are registered. Don't "helpfully" split that into two diﬀerent UI
messages.

What the server does with the token
It calls Facebook's debug_token  and checks the token was issued for our app id, then
reads the proﬁle. A token from any other Facebook app is refused. This matters for you only
in one way: the token must come from the Facebook app conﬁgured for Daketi, so use the
app id the backend dev gives you, not one from another project.

needsEmail  - the case worth handling properly
Facebook does not always give us an email. The user can deny the permission, and
phone-only Facebook accounts have none at all, which is common in Pakistan. Those
accounts are created successfully with 
email: null  and needsEmail: true .
Such a user can play normally, but until they add an email they cannot:
reset a password (there's nowhere to send the link),
be credited as someone's referral (credit requires a veriﬁed email).
So when needsEmail  is true , prompt for an email address at a sensible moment and send it
with PATCH /api/auth/me . Don't block the game on it.
Sign-in methods on the user object
Every endpoint that returns a user now includes two booleans, so the app can show the right
options:
facebookLinked  - true  if this account can sign in with Facebook.
hasPassword  - false  for a Facebook-only account. Hide "change password" for those; POST
/api/auth/change-password  will refuse with a message telling them to use "forgot password"
to set one, which works as long as they have an email.

Email links and deep linking
Reset and veriﬁcation emails link to the web app, not the mobile app:
https://game.daketi.pk/?resetToken=<token>
https://game.daketi.pk/?verifyToken=<token>
(The base URL is the backend's 
FRONTEND_URL  env var.) A user who taps that link on their
phone lands in the browser, which completes the ﬂow on the web - it works, but it leaves the
app. If you want these to open the Flutter app instead, that needs a coordinated change:
Android App Links / iOS Universal Links on your side, plus the backend pointing 
FRONTEND_URL
at a link that resolves to both. Talk to the backend dev before building against these
URLs - they're the one thing here that can't be handled app-side alone. Either way, the token
is just a query parameter: however you get it, you POST it to /verify-email  or /reset-
password .
Token handling
token  is a JWT, valid for 30 days. Store it securely ( flutter_secure_storage , not plain
SharedPreferences ) and send it as Authorization: Bearer <token>  on any endpoint that
needs it - and as the token  ﬁeld on join_game , which is the only way games get

Rate Limits and Error Handling
The auth endpoints are rate-limited per IP address (see the table in User Accounts for the
per-endpoint numbers). Nothing else - game creation, game state, leaderboard, and every
Socket.io event - is limited today.
When a limit is hit you get:
HTTP 429
{ "success": false, "error": "Too many requests - p lease try again later" }
Standard 
RateLimit-*  response headers come back on every call to a limited endpoint (not
just the 429), so you can read RateLimit-Remaining  / RateLimit-Reset  if you want to warn
before the wall.
T wo things to plan for:
1. Handle 429 explicitly. An app that only checks 
success  will show "Login failed" to a
user who actually just needs to wait - a confusing dead end, especially on the 3/hour
forgot-password limiter. Show the 
error  message and, ideally, the wait time from
RateLimit-Reset .
2. Limits are per IP , not per user. Everyone on one oﬃce wiﬁ or behind one mobile-carrier
NAT shares a bucket. Expect to hit this during team testing - it's not a bug, and retrying
immediately makes it worse.

How position works
Position is computed on read, never stored: the queue is ranked by (verified referrals
DESC, joined_at ASC) . T wo consequences worth designing the UI around:
A user's number can move without them doing anything - someone ahead gets
invited, or a rival earns a referral. Re-read /api/waitlist/me  when the screen is shown
rather than caching a number from yesterday.
A referral only counts once the referred account veriﬁes its email. That's
deliberate - referrals aﬀect position, so unveriﬁed signups would be farmable.
referralCount  is what counts; pendingReferralCount  is referred-but-unveriﬁed, exposed so
"I invited 5 but it says 3" is answerable in the UI instead of looking like a bug.

Client → Server Events
1. Join Game
Works the same for solo and multiplayer games - call it right after creating (or whenever
joining an existing) room.
socket.emit('join_game', {
  'gameId': '0472',
  'playerName': 'John',
  'token': authToken,            // optional JWT - omit for guests, see below
  'reconnectToken': savedToken,  // optional - send  it back to reclaim your seat
}, (response) {

  // For solo games, the game auto-starts as soon a s you (the 1 human) join.
  // For multiplayer rooms, status stays "waiting" until everyone is ready.
  print(response);
});
Errors: 
"Game not found" , "Game is full"  (room already has maxPlayers  players).
token  is how a game gets recorded against an account. Pass the JWT from signup/login
(the same one you'd put in an Authorization  header) and, when the game ﬁnishes, the result
is written to that user's record - feeding /api/auth/me  stats, /api/auth/me/history  and the
leaderboard.
Whenever you have a logged-in user, send it. If you don't:
The join still succeeds and the game plays identically - the player is simply treated as a
guest.
Nothing is saved. No stats, no history row, no leaderboard entry, and there's no way to
backﬁll it afterwards - the game is gone from Redis by the time anyone notices.
An invalid or expired token is treated exactly like no token: a silent guest session, no error.
So a user whose 30-day JWT quietly expired keeps playing while their games stop counting,
with nothing in the response to reveal it. Guard against it on the client: call 
/api/auth/me  on
app start (and on resume) and force a re-login on 401  before letting them into a game.
playerName  is still yours to choose and is not taken from the account - pass the account's
name yourself if you want them to match.
Reconnecting: reconnectToken
Every join response carries a reconnectToken . Persist it, and send it back on every
subsequent join for that game. This is not optional polish on mobile - without it a
reconnect loses the game.

--- PAGE 27 ---
Daketi API Guide · 30 September 2026 Page 27 of 41
Here's why. The server binds your seat to the socket id, and Socket.io issues a new socket
id every time it reconnects - which on a phone happens constantly: backgrounding the
app, a screen lock, wiﬁ dropping to cellular, a tunnel. On that new id the server no longer
recognises you, and before this token existed the outcome was one of:
a solo game refused you with "Game is full"  (the room is full at 1 human + the AI) - the
game was unrecoverable;
a multiplayer room handed you a second seat, stranding your real hand and score in the
orphaned one.
Send the token and the server moves your existing seat - hand, stack, score, ready state -
onto the new socket, and answers with 
reclaimed: true :
// first join
{ success: true, playerId: 'abc123', reconnectToken : '9f2c…', reclaimed: false, gameState: 
{...} }
// after a reconnect, same game
{ success: true, playerId: 'xyz789', reconnectToken : '9f2c…', reclaimed: true,  gameState: 
{...} }
Notes:
playerId  changes on reclaim (it's the new socket id). Always re-read it from the
response and re-read player ids from gameState ; never hold the old one.
The token is per game, not per user. Store it against the gameId  and drop it when the
game ends.
Treat it as a secret - it's what proves the seat is yours. It's only ever sent to the seat's
owner, never in a broadcast. Don't log it or show it in a UI.
Logged-in users get a fallback: if you have no stored reconnectToken  but do send a
valid token  (JWT), the server matches on the account instead. That covers an app
reinstall. Guests have no fallback - the token is the only way back.
Sending neither is still supported and behaves exactly as before (new seat, or "Game is
full" ), so nothing breaks if you ship this in stages.

Card Format
Cards are represented as 2-character strings:
Format: 
[Value][Suit]
Values:
2-9 : Number cards
T : 10
J : Jack
Q : Queen
K : King
A : Ace
Suits:
H : Hearts ♥
D : Diamonds ♦
C : Clubs ♣
S : Spades ♠
Examples:
AH  = Ace of Hearts
KD  = King of Diamonds
TD  = 10 of Diamonds
7C  = 7 of Clubs
Game Rules the Client Must Respect
These aren't just documentation - the server enforces all of them and will reject illegal
requests, but your UI should proactively disable illegal moves rather than let the player tap
them and see an error:
1. Can't discard a card matching the table. If any card in 
table  shares a value with the
card the player has selected, "discard" must be hidden/disabled for it - only "capture" is
legal. Check via 
get_actions  or by comparing the selected card's value against table .
2. Only the top stack card is stealable, and only if its value isn't in protectedValues .
3. A value becomes protected once all 4 copies are in someone's stack - not just oﬀ
the table/deck. A copy still sitting in any player's hand does not count as protected yet.
4. Extending your own stack requires the played card's value to match your current top
stack card exactly.

5. Exactly one card must be discarded to end a turn - but combo chains let a player
capture/steal/extend repeatedly (auto-drawing after each) before ﬁnally discarding.
6. During the endgame (deck empty), actions stop auto-drawing; if an action empties a
player's hand entirely, their turn ends automatically without needing a discard.

Common Gotchas
1. Card IDs are strings, not objects ( "AH"  not {value: "A", suit: "H"} ).
2. Opponent hands are hidden - you'll see ["hidden", "hidden", ...] ; opponent stacks
only show their top card, not the full stack.
3. Actions auto-draw cards - after capture/steal/extend, a new card is automatically
drawn (unless the deck is empty).
4. Discard always ends the turn, and can't be used on a card that matches something on
the table (see Game Rules).
5. Protected cards - check protectedValues  to see which values can no longer be stolen;
note the array order is chronological (when each value became protected), not sorted by
rank.
6. 
gameId  is a string, even though it looks numeric ( "0472" ) - don't parse it as an int, and
don't strip leading zeros.
7. transports: ['websocket']  is mandatory - omitting it will simply fail to connect (see
Socket.io Setup).
8. playerId  comes from the socket, not the REST call - the REST create-game
endpoints only return gameId ; call join_game  over the socket to get your actual playerId .
9. Account login is separate from game identity - being logged in ( /api/auth/* ) doesn't
automatically set your playerName  when joining a game; you still pass a name explicitly to
join_game .

10. Persist reconnectToken  or reconnects lose the game - a new socket id means a new
identity to the server. On mobile this ﬁres constantly (backgrounding, wiﬁ↔cellular). See
Reconnecting.
11. playerId  is not stable across a reconnect - it's the socket id, and it changes when the
seat is reclaimed. Re-read it from every join response and take player ids from gameState ,
never from memory.
12. Forgetting token  on join_game  silently loses the result - the game plays ﬁne, then
nothing is recorded. An expired token behaves the same way, with no error. See Join
Game.
13. Response key casing is mixed - the user object is camelCase  ( emailVerified ,
dateOfBirth ), but stats, history and leaderboard rows come straight from SQL as
snake_case  ( games_won , is_winner , played_at ). Inside a history row's opponents , it's back
to camelCase  ( isWinner ). Check the examples rather than guessing.
14. PATCH /api/auth/me  needs name  every time - it's a full update, so sending only
dateOfBirth  fails with 400 "Name is required" .
15. Handle 429  - the auth endpoints are rate-limited per IP, and a client that only checks
success  will report "login failed" to someone who just needs to wait.
16. Password reset and veriﬁcation emails point at the web app, not the app - deep
linking into Flutter needs a backend change too. See Email links and deep linking.
